키(Key) 완전 정복

테이블에서 데이터를 식별하고 연결하는 방법

데이터베이스에서 키(Key)는 테이블 안에서 행(Row)을 식별하거나, 다른 테이블과 연결하는 역할을 합니다. 게시판의 4가지 키를 하나씩 살펴봅니다.

🔑 기본키 (Primary Key)

테이블에서 각 행을 유일하게 식별하는 컬럼입니다. 중복될 수 없고, NULL이 될 수 없습니다.

이런 역할을 합니다
  • 행마다 반드시 달라야 함
  • 빈 값(NULL) 불가
  • 한 테이블에 반드시 하나만 존재
  • AUTOINCREMENT로 DB가 자동 부여
게시판 기본키 
-- 모든 테이블의 id가 기본키
id INTEGER PRIMARY KEY AUTOINCREMENT

-- users: id=1, id=2, id=3...
-- posts: id=1, id=2, id=3...
-- comments: id=1, id=2, id=3...

🔗 외래키 (Foreign Key)

다른 테이블의 기본키를 참조하는 컬럼입니다. 테이블 간의 관계를 만드는 연결 고리입니다.

이런 역할을 합니다
  • 참조하는 테이블에 실제로 존재하는 값만 허용
  • 없는 user_id를 가진 게시글 생성 불가
  • 테이블 간 관계를 DB가 자동으로 보장
게시판 외래키 
-- posts.user_id → users.id 참조
user_id INTEGER,
FOREIGN KEY (user_id)
  REFERENCES users(id)

-- comments는 외래키 2개
FOREIGN KEY (post_id) REFERENCES posts(id)
FOREIGN KEY (user_id) REFERENCES users(id)

🚫 유니크 키 (Unique Key)

기본키처럼 중복을 허용하지 않지만, NULL은 허용되고 한 테이블에 여러 개 둘 수 있습니다.

기본키와의 차이
구분 PK UQ
중복 불가 ✅ ✅
NULL 불가 ✅ ❌
테이블당 개수 1개만 여러 개 가능
게시판에서의 UNIQUE 
-- 같은 아이디로 가입 불가
username TEXT UNIQUE NOT NULL

-- alice가 이미 있으면
INSERT INTO users (username...)
VALUES ('alice'...)
-- → UNIQUE constraint failed 오류

🔑🔑 복합 기본키 (Composite Key)

두 개 이상의 컬럼을 합쳐서 기본키로 사용합니다. 각 컬럼은 중복될 수 있지만, 조합은 유일해야 합니다.

좋아요 테이블에서의 예시

user_id post_id 가능?
1 1 ✅ 첫 좋아요
1 2 ✅ 다른 글
2 1 ✅ 다른 사람
1 1 ❌ 중복!
복합 기본키 선언 
CREATE TABLE likes (
  user_id INTEGER,
  post_id INTEGER,
  -- 두 컬럼의 조합이 PK
  PRIMARY KEY (user_id, post_id)
);

한눈에 보는 키 정리

종류 역할 게시판 예시
PK 기본키 행의 고유 식별자 users.id, posts.id, comments.id
FK 외래키 다른 테이블 참조 posts.user_id, comments.post_id
UQ 유니크키 중복 방지 users.username
CPK 복합키 컬럼 조합으로 식별 likes(user_id, post_id)

데이터 타입

컬럼에 어떤 종류의 값을 담을지 결정한다

테이블을 설계할 때 각 컬럼에 어떤 타입의 데이터를 넣을지 지정해야 합니다. 타입이 맞지 않으면 저장도, 연산도 제대로 되지 않습니다.

INTEGER
정수

소수점 없는 숫자. id, 개수, 순서 등에 씁니다.

id = 1 user_id = 3 like_count = 42
게시판: id, user_id, post_id
TEXT
문자열

길이 제한 없는 문자열. 이름, 제목, 내용 등 거의 모든 문자 데이터에 씁니다.

username = "alice" title = "첫 번째 글"
게시판: username, title, content, password
REAL
실수 (소수)

소수점이 있는 숫자. 가격, 평점, 위도/경도 등에 씁니다.

price = 9900.50 rating = 4.5 lat = 37.5665
게시판: 해당 없음
DATETIME
날짜+시간

날짜와 시간을 함께 저장. 생성일, 수정일, 만료일 등에 씁니다.

created_at = "2026-05-20 09:30:00"
게시판: created_at
BOOLEAN
참/거짓

참(1) 또는 거짓(0). 활성화 여부, 공개/비공개, 읽음 여부 등에 씁니다.

is_active = 1 is_public = 0 is_read = 1
SQLite는 내부적으로
INTEGER 0/1로 처리
BLOB
바이너리

이미지, 파일 등 바이너리 데이터. 실무에서는 파일 자체보다 저장 경로(URL)를 TEXT로 넣는 경우가 많습니다.

thumbnail_url = "/images/abc.jpg"
대부분 URL을
TEXT로 저장

타입 선택 기준

상황 타입 이유
사용자 ID, 게시글 번호 INTEGER 숫자 연산·비교, JOIN에 유리
이름, 제목, 내용 TEXT 길이 예측 불가, 자유로운 문자열
가격, 평점 REAL 소수점 필요
작성일, 수정일 DATETIME 날짜 비교·정렬 가능
공개여부, 활성화 INTEGER (0/1) BOOLEAN이 없는 DB도 많음
이미지, 첨부파일 TEXT (URL) 파일은 S3 등 별도 저장, DB엔 경로만
⚠️

전화번호는 INTEGER가 아닌 TEXT로 저장합니다. 010-1234-5678처럼 하이픈이 들어가고, 앞자리 0이 사라지는 문제가 생기기 때문입니다.

ERD — 설계도 읽기

Entity Relationship Diagram

ERD는 데이터베이스의 설계 청사진입니다. 코드를 작성하기 전에 테이블 구조와 관계를 시각적으로 정리합니다.

게시판 ERD — ERDCloud
PK Primary Key — 기본키 (행의 고유 식별자) FK Foreign Key — 외래키 (다른 테이블 참조) UQ Unique — 중복 불가 NN Not Null — 비워둘 수 없음
📐

ERD를 먼저 그리는 이유: 코드를 짜다가 설계가 잘못됐음을 발견하면 전체를 뒤엎어야 합니다. 설계 단계에서 ERD로 검토하면 수정 비용이 거의 없습니다.

server/db.js — 실제 테이블 생성 SQL 
CREATE TABLE IF NOT EXISTS users (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  username   TEXT    UNIQUE NOT NULL,
  password   TEXT    NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS posts (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  title      TEXT    NOT NULL,
  content    TEXT    NOT NULL,
  user_id    INTEGER NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id)   ← 외래키
);

CREATE TABLE IF NOT EXISTS comments (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  content    TEXT    NOT NULL,
  post_id    INTEGER NOT NULL,
  user_id    INTEGER NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (post_id) REFERENCES posts(id),   ← 외래키
  FOREIGN KEY (user_id) REFERENCES users(id)    ← 외래키
);

관계 — 1:N 이해하기

테이블들이 어떻게 연결되는가

게시판의 모든 관계는 1:N (일대다)입니다. "1" 쪽 하나에 "N" 쪽 여러 개가 연결됩니다.

👤 users
1명
1 : N
여러 게시글 작성
📝 posts
N개
1 : N
여러 댓글 달림
💬 comments
N개
🎯

설계 법칙: 1:N에서 외래키는 항상 "N" 쪽 테이블에 둡니다.
사용자 1명 → 게시글 N개이므로, user_id는 posts 테이블에 있습니다.

데이터로 이해하기

users.id username posts.id title user_id
1 alice → 1 첫 번째 글 1
2 bob → 2 두 번째 글 2
→ 3 세 번째 글 1

alice(id=1)가 게시글 1번·3번을, bob(id=2)이 2번을 작성했습니다. user_id가 연결 고리입니다.

7

외래키와 데이터 무결성

DB가 스스로 데이터를 지키는 방법

외래키는 단순한 숫자가 아닙니다. DB가 자동으로 참조 무결성을 보장합니다.

❌ 외래키가 막아주는 상황들

  • 존재하지 않는 user_id를 가진 게시글 생성 시도
  • 댓글이 달린 게시글을 댓글 삭제 없이 지우려는 시도
  • 탈퇴한 사용자 id를 새 게시글에 연결하려는 시도
⚠️

삭제 순서가 중요합니다. 게시글을 삭제할 때 딸린 댓글을 먼저 지워야 합니다.
부모(posts) 먼저 지우면 자식(comments)의 외래키가 허공을 가리켜서 오류 발생합니다.

// routes/posts.js — 순서가 중요!
db.prepare("DELETE FROM comments WHERE post_id = ?").run(id);  ← 자식 먼저
db.prepare("DELETE FROM posts WHERE id = ?").run(id);           ← 부모 나중

실습 — 좋아요 기능 설계하기

N:M 관계와 중간 테이블
🖊 실습 과제

게시글에 좋아요 기능을 추가한다면?

한 사용자가 여러 게시글에 좋아요를 누를 수 있고,
한 게시글에 여러 사용자가 좋아요를 누를 수 있습니다.

ERDCloud에서 likes 테이블을 직접 설계해보세요.

힌트 — 왜 중간 테이블이 필요한가

users와 posts는 N:M (다대다) 관계입니다. 1:N과 달리 한쪽에 외래키를 두는 것만으로는 표현할 수 없습니다.

👤 users
N명
N : M
📝 posts
M개
↓ N:M은 중간 테이블로 분리
👤 users
1 : N
❤️ likes
(중간 테이블)
N : 1
📝 posts

정답 — likes 테이블 설계

likes 테이블 
CREATE TABLE likes (
  user_id    INTEGER NOT NULL,
  post_id    INTEGER NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, post_id),            ← 복합키: 같은 사람이 같은 글에 중복 좋아요 불가
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (post_id) REFERENCES posts(id)
);
💡

복합 기본키: PRIMARY KEY (user_id, post_id)는 두 컬럼의 조합이 유일해야 한다는 뜻입니다. 같은 사람이 같은 글에 좋아요를 두 번 누르면 DB가 자동으로 막습니다.

9

설계 원칙 정리

좋은 설계를 판단하는 기준

AI가 SQL 쿼리는 대신 짜줄 수 있지만, 설계는 사람이 판단해야 합니다. 정답이 없고, 상황에 맞는 트레이드오프를 선택하는 것이 핵심입니다.

하나의 컬럼 = 하나의 값

배열이나 JSON을 한 칸에 넣지 않습니다. 나중에 검색·수정이 어려워집니다. (단, 의도적 예외는 허용)

중복 데이터는 분리

같은 정보가 여러 곳에 반복되면 테이블을 분리합니다. 수정 시 한 곳만 바꾸면 됩니다.

N:M은 중간 테이블로

다대다 관계는 직접 표현하지 않고, 1:N 두 개로 분리합니다.

완벽한 설계는 없다

정규화 vs 성능, 단순함 vs 확장성. 상황에 맞게 트레이드오프를 선택합니다.

🎓

AI 시대의 DB 역량: SQL 문법 암기보다 어떤 테이블을 만들지, 관계를 어떻게 설정할지가 훨씬 중요합니다. 설계를 잘 설명할 수 있으면 AI가 나머지 쿼리를 짜줍니다.

정규화 기초

중복을 제거하고 구조를 정돈하는 방법

정규화(Normalization)는 테이블의 중복과 이상(anomaly)을 줄이기 위해 구조를 단계적으로 정돈하는 과정입니다. 1NF → 2NF → 3NF 순서로 조건이 점점 엄격해집니다.

① 1NF — 원자값 (Atomic Values)

하나의 칸(셀)에는 하나의 값만 들어가야 합니다. 목록·배열을 한 칸에 넣으면 1NF 위반입니다.

❌ 1NF 위반
posts 테이블 ┌────┬──────────┬──────────────────┐ │ id │ title │ tags │ ├────┼──────────┼──────────────────┤ │ 1 │ 안녕 │ 공지,이벤트,중요 │ ← 한 칸에 여러 값 │ 2 │ 질문있어요│ 질문,도움요청 │ └────┴──────────┴──────────────────┘
✅ 1NF 준수
post_tags 테이블 (분리) ┌─────────┬──────────┐ │ post_id │ tag │ ├─────────┼──────────┤ │ 1 │ 공지 │ │ 1 │ 이벤트 │ │ 1 │ 중요 │ │ 2 │ 질문 │ └─────────┴──────────┘

② 2NF — 부분 종속 제거 (No Partial Dependency)

복합 기본키를 가진 테이블에서, 일반 컬럼이 기본키 전체에 종속되어야 합니다. 기본키의 일부에만 종속되면 2NF 위반입니다.

❌ 2NF 위반 (복합키: post_id + user_id)
post_likes 테이블 ┌─────────┬─────────┬──────────┐ │ post_id │ user_id │ username │ ← user_id에만 종속 ├─────────┼─────────┼──────────┤ │ 1 │ 10 │ alice │ │ 2 │ 10 │ alice │ ← 중복 발생 └─────────┴─────────┴──────────┘
✅ 2NF 준수 (users 테이블 분리)
post_likes users ┌─────────┬─────────┐ ┌────┬──────────┐ │ post_id │ user_id │ │ id │ username │ ├─────────┼─────────┤ ├────┼──────────┤ │ 1 │ 10 │ │ 10 │ alice │ │ 2 │ 10 │ └────┴──────────┘ └─────────┴─────────┘
💡

우리 게시판의 posts 테이블은 단일 기본키(id)를 사용하므로 2NF 문제가 발생하지 않습니다. 2NF는 주로 복합 기본키를 쓰는 테이블(예: post_tags, likes)에서 주의해야 합니다.

③ 3NF — 이행 종속 제거 (No Transitive Dependency)

일반 컬럼이 기본키에만 종속되어야 합니다. 일반 컬럼 A → 일반 컬럼 B 형태의 종속(이행 종속)이 있으면 3NF 위반입니다.

❌ 3NF 위반
posts 테이블 ┌────┬──────────┬─────────┬──────────────┐ │ id │ title │ user_id │ user_email │ ├────┼──────────┼─────────┼──────────────┤ │ 1 │ 안녕 │ 10 │ a@example.com│ │ 2 │ 질문 │ 10 │ a@example.com│ ← 중복 └────┴──────────┴─────────┴──────────────┘ id → user_id → user_email (이행 종속)
✅ 3NF 준수
posts users ┌────┬──────────┬─────────┐ ┌────┬──────────────┐ │ id │ title │ user_id │ │ id │ email │ ├────┼──────────┼─────────┤ ├────┼──────────────┤ │ 1 │ 안녕 │ 10 │ │ 10 │ a@example.com│ │ 2 │ 질문 │ 10 │ └────┴──────────────┘ └────┴──────────┴─────────┘

정규화 단계 요약

단계 조건 위반 예시 해결 방법
1NF 각 칸에 원자값 하나만 tags = "공지,이벤트" tags 전용 테이블 분리
2NF 부분 종속 없음 (복합키) likes에 username 저장 users 테이블로 분리
3NF 이행 종속 없음 posts에 user_email 저장 users 테이블로 분리

의도적 비정규화 — 언제 규칙을 깨는가?

정규화가 항상 정답은 아닙니다. 성능·편의·아키텍처 때문에 의도적으로 정규화를 위반하기도 합니다.

PostgreSQL 배열 타입

하나의 칸에 여러 값 저장 (1NF 위반). 태그·권한처럼 단순 목록 조회만 하면 별도 테이블보다 빠르고 간편합니다.

MSA (마이크로서비스)

서비스마다 DB가 분리되어 동일한 데이터를 여러 DB에 중복 저장합니다. 독립 배포·확장성을 위한 의도적 선택입니다.

캐싱·집계 컬럼

댓글 수를 매번 COUNT하지 않고 posts.comment_count에 저장. 조회 성능을 위해 중복을 허용합니다.

🎯

핵심 원칙: 정규화는 기본값이고, 비정규화는 의도적 예외입니다. 비정규화할 때는 반드시 왜 깨는지를 팀이 알고 있어야 합니다. 이유 없는 비정규화는 버그의 온상이 됩니다.
