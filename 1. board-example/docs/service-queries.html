인증 — auth.js

회원가입·로그인 요청 처리 / routes/auth.js
1
아이디 중복 확인
회원가입 시 입력한 아이디가 이미 존재하는지 먼저 확인합니다. 이미 있으면 가입을 막고 409 에러를 반환합니다.
POST /api/auth/register SELECT WHERE
routes/auth.js — POST /register 
SELECT id
FROM   users
WHERE  username = ?          -- ? 자리에 사용자가 입력한 아이디가 들어감
각 절 설명
SELECT id 존재 여부만 확인하면 되므로 id 하나만 가져옵니다. SELECT *는 불필요한 데이터(비밀번호 등)까지 읽으므로 피합니다.
FROM users 유저 테이블에서 조회합니다.
WHERE 특정 username을 가진 행만 필터링합니다. ?는 플레이스홀더로, 실제 값은 코드에서 안전하게 바인딩됩니다 (SQL 인젝션 방지).
💡

결과가 있으면 이미 사용 중인 아이디 → 409 반환. 결과가 없으면 다음 단계(INSERT)로 진행합니다.

2
회원가입 — 유저 삽입
중복 확인을 통과한 뒤, 해시된 비밀번호와 함께 새 유저를 저장합니다.
POST /api/auth/register INSERT
routes/auth.js — POST /register 
INSERT INTO users (username, password)
VALUES (?, ?)     -- ? : 아이디, bcrypt 해시된 비밀번호
각 절 설명
INSERT INTO 지정한 테이블에 새 행을 추가합니다.
(username, password) 값을 넣을 컬럼을 명시합니다. id와 created_at은 명시하지 않아도 DB가 자동으로 채웁니다.
VALUES 삽입할 실제 값을 순서대로 지정합니다. password는 코드에서 bcrypt.hashSync()로 해시한 뒤 전달됩니다.
⚠️

비밀번호는 절대 평문으로 저장하지 않습니다. bcrypt로 해싱한 값이 DB에 저장됩니다. 해시는 단방향이라 원본 비밀번호를 역산할 수 없습니다.

3
로그인 — 유저 조회
아이디로 유저를 찾아 비밀번호 해시를 가져옵니다. 이후 코드에서 입력 비밀번호와 해시를 비교해 인증합니다.
POST /api/auth/login SELECT WHERE
routes/auth.js — POST /login 
SELECT *
FROM   users
WHERE  username = ?
각 절 설명
SELECT * 유저의 모든 컬럼을 가져옵니다. 비밀번호 해시 비교와 JWT 토큰 발급에 id, username, password 모두 필요하기 때문입니다.
WHERE 입력한 아이디와 일치하는 유저 한 명만 가져옵니다. username은 UNIQUE 제약이 있어 결과는 항상 0개 또는 1개입니다.
💡

쿼리 결과가 없으면 → 존재하지 않는 아이디. 결과가 있어도 bcrypt.compareSync()가 false면 → 비밀번호 불일치. 둘 다 401로 동일하게 처리합니다 (어느 쪽이 틀렸는지 알려주지 않는 것이 보안상 올바릅니다).

📝

게시글 — posts.js

목록·상세 조회, 작성, 삭제 / routes/posts.js
4
게시글 목록 조회
메인 화면에 표시하는 전체 게시글 목록입니다. 각 게시글의 작성자 이름과 댓글 수를 함께 가져옵니다. 서비스에서 가장 복잡한 쿼리입니다.
GET /api/posts SELECT JOIN × 2 GROUP BY
routes/posts.js — GET / 
SELECT   posts.id,
         posts.title,
         posts.created_at,
         users.username,
         COUNT(comments.id) AS comment_count
FROM     posts
JOIN     users    ON posts.user_id  = users.id
LEFT JOIN comments ON comments.post_id = posts.id
GROUP BY posts.id
ORDER BY posts.created_at DESC
각 절 설명
SELECT 컬럼 지정 필요한 컬럼만 명시적으로 선택합니다. posts.id처럼 테이블.컬럼 형식을 쓰는 이유는 두 테이블에 같은 이름의 컬럼(id, created_at)이 있어 어느 테이블의 것인지 명확히 해야 하기 때문입니다.
COUNT(comments.id) 각 게시글에 달린 댓글 수를 셉니다. COUNT(*)가 아닌 COUNT(comments.id)를 쓰는 이유: 댓글이 0개인 게시글은 LEFT JOIN 결과의 comments.id가 NULL이 되는데, COUNT는 NULL을 세지 않아 정확히 0을 반환합니다.
JOIN users posts 테이블에는 user_id(숫자)만 있고 작성자 이름이 없습니다. INNER JOIN으로 users 테이블을 연결해 username을 가져옵니다. 작성자가 반드시 존재하므로 INNER JOIN을 씁니다.
LEFT JOIN comments 댓글이 하나도 없는 게시글도 목록에 나와야 하므로 LEFT JOIN을 씁니다. INNER JOIN을 쓰면 댓글이 없는 게시글은 결과에서 제외됩니다.
GROUP BY posts.id LEFT JOIN으로 댓글 수만큼 행이 늘어나므로(게시글 1개에 댓글 3개면 3행), GROUP BY로 게시글 기준으로 다시 묶습니다. 이 과정에서 COUNT()가 각 그룹의 댓글 수를 계산합니다.
ORDER BY … DESC 최신 게시글이 위에 오도록 내림차순 정렬합니다.
🔍

LEFT JOIN vs INNER JOIN: 댓글이 없는 게시글을 포함하려면 LEFT JOIN이 필수입니다. INNER JOIN은 양쪽 테이블에 모두 매칭되는 행만 결과에 포함합니다.

5
게시글 상세 조회
특정 게시글 하나를 ID로 조회합니다. 상세 페이지 진입 시 실행됩니다.
GET /api/posts/:id SELECT JOIN WHERE
routes/posts.js — GET /:id 
SELECT   posts.*,
         users.username
FROM     posts
JOIN     users ON posts.user_id = users.id
WHERE    posts.id = ?          -- ? : URL 파라미터 :id
각 절 설명
posts.* posts 테이블의 모든 컬럼을 가져옵니다. 상세 페이지는 제목·내용·작성일을 모두 보여줘야 합니다. users.*가 아닌 posts.*만 와일드카드를 쓰는 이유는 users의 password가 포함되는 것을 막기 위해서입니다.
JOIN users 작성자 이름을 가져오기 위해 JOIN합니다. Q4와 같은 원리입니다.
WHERE posts.id = ? URL의 :id 파라미터로 특정 게시글 하나만 필터링합니다. id는 PK(기본키)이므로 결과는 0개 또는 1개입니다.
6
게시글 작성
로그인한 사용자가 새 게시글을 작성할 때 실행됩니다. JWT 토큰 검증 후에만 실행됩니다.
POST /api/posts INSERT
routes/posts.js — POST / 
INSERT INTO posts (title, content, user_id)
VALUES (?, ?, ?)   -- ? : 제목, 내용, 로그인한 유저의 id
각 절 설명
(title, content, user_id) 세 컬럼만 명시합니다. id는 AUTOINCREMENT, created_at은 DEFAULT CURRENT_TIMESTAMP로 DB가 자동 채웁니다.
user_id = req.user.id 세 번째 ?에는 JWT 토큰에서 추출한 로그인 유저의 ID가 들어갑니다. 프론트가 직접 user_id를 보내는 게 아니라, 서버가 토큰에서 추출하기 때문에 위변조가 불가능합니다.
7
게시글 삭제 전 — 존재·권한 확인
삭제 요청이 오면 먼저 게시글이 존재하는지, 요청한 사람이 작성자인지 확인합니다. 이 쿼리로 확인 후 실제 삭제 쿼리를 실행합니다.
DELETE /api/posts/:id SELECT WHERE
routes/posts.js — DELETE /:id (1단계: 확인) 
SELECT *
FROM   posts
WHERE  id = ?            -- ? : URL 파라미터 :id
각 절 설명 + 코드 연계
결과 없음 게시글이 존재하지 않음 → 코드에서 404 반환.
post.user_id 비교 가져온 post.user_id와 JWT 토큰의 req.user.id를 코드에서 비교합니다. 다르면 403 반환. 이 로직은 SQL이 아닌 JavaScript에서 처리합니다.
⚠️

권한 확인을 절대 생략하면 안 됩니다. 확인 없이 바로 DELETE를 실행하면 누구든 다른 사람의 게시글을 삭제할 수 있습니다.

8
게시글 삭제 시 — 댓글 먼저 삭제
게시글에 달린 댓글은 posts 테이블을 참조합니다. 게시글을 먼저 지우면 참조 무결성 오류가 나므로, 댓글을 먼저 삭제합니다.
DELETE /api/posts/:id DELETE WHERE
routes/posts.js — DELETE /:id (2단계: 댓글 삭제) 
DELETE FROM comments
WHERE       post_id = ?      -- ? : 삭제할 게시글 id
각 절 설명
DELETE FROM comments posts 테이블이 아닌 comments 테이블의 행을 삭제합니다.
WHERE post_id = ? 해당 게시글에 달린 댓글만 삭제합니다. WHERE 없이 실행하면 전체 댓글이 삭제되므로 반드시 필요합니다.
💡

실무에서는 CASCADE로 자동화합니다. FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE를 선언하면 게시글 삭제 시 댓글이 자동으로 함께 삭제됩니다. 이 서비스는 수동으로 처리하고 있습니다.

9
게시글 삭제
댓글을 먼저 지운 뒤 실제 게시글을 삭제합니다. Q8 → Q9 순서로 실행됩니다.
DELETE /api/posts/:id DELETE WHERE
routes/posts.js — DELETE /:id (3단계: 게시글 삭제) 
DELETE FROM posts
WHERE       id = ?          -- ? : 삭제할 게시글 id
실행 순서 정리
① Q7 게시글 존재·권한 확인 (SELECT)
② Q8 해당 게시글의 댓글 전체 삭제 (DELETE FROM comments)
③ Q9 게시글 삭제 (DELETE FROM posts) — 이 순서여야 외래키 오류 없이 삭제됩니다.
💬

댓글 — comments.js

댓글 목록·작성·삭제 / routes/comments.js
10
댓글 목록 조회
게시글 상세 페이지에서 해당 게시글의 댓글 전체를 불러옵니다. 작성자 이름과 함께 오래된 순으로 정렬합니다.
GET /api/posts/:postId/comments SELECT JOIN WHERE
routes/comments.js — GET / 
SELECT   comments.*,
         users.username
FROM     comments
JOIN     users ON comments.user_id = users.id
WHERE    comments.post_id = ?    -- ? : URL 파라미터 :postId
ORDER BY comments.created_at ASC
각 절 설명
comments.* 댓글의 모든 컬럼을 가져옵니다. Q5(posts.*)와 같은 원리로 users.*는 사용하지 않아 비밀번호가 노출되지 않습니다.
JOIN users 댓글 테이블에는 user_id만 있으므로 JOIN으로 작성자 이름을 가져옵니다.
WHERE comments.post_id = ? 해당 게시글의 댓글만 필터링합니다. 이 조건이 없으면 전체 댓글이 반환됩니다.
ORDER BY … ASC 댓글은 먼저 달린 것이 위에 오도록 오름차순 정렬합니다. 게시글 목록(Q4)과 반대 방향입니다.
11
댓글 작성 전 — 게시글 존재 확인
댓글을 작성하기 전에 해당 게시글이 실제로 존재하는지 확인합니다. 삭제된 게시글에 댓글이 달리는 것을 막습니다.
POST /api/posts/:postId/comments SELECT WHERE
routes/comments.js — POST / (1단계: 확인) 
SELECT id
FROM   posts
WHERE  id = ?            -- ? : URL 파라미터 :postId
각 절 설명
SELECT id Q1과 같은 패턴입니다. 존재 여부만 확인하므로 id 하나만 가져옵니다.
결과 없음 → 404 게시글이 없으면 404를 반환하고 INSERT를 실행하지 않습니다.
12
댓글 작성
게시글 존재를 확인한 뒤 댓글을 저장합니다.
POST /api/posts/:postId/comments INSERT
routes/comments.js — POST / (2단계: 삽입) 
INSERT INTO comments (content, post_id, user_id)
VALUES (?, ?, ?)   -- ? : 댓글 내용, 게시글 id, 로그인 유저 id
각 절 설명
post_id URL 파라미터 :postId에서 가져옵니다. 어느 게시글의 댓글인지 외래키로 연결합니다.
user_id Q6(게시글 작성)과 동일하게 JWT 토큰에서 추출한 req.user.id가 들어갑니다.
13
댓글 삭제 전 — 존재·권한 확인
Q7(게시글 삭제 전 확인)과 동일한 패턴입니다. 댓글이 존재하는지, 요청자가 작성자인지 확인합니다.
DELETE /api/posts/:postId/comments/:commentId SELECT WHERE
routes/comments.js — DELETE /:commentId (1단계: 확인) 
SELECT *
FROM   comments
WHERE  id = ?            -- ? : URL 파라미터 :commentId
각 절 설명
결과 없음 → 404 댓글이 이미 삭제됐거나 없을 때 404 반환.
comment.user_id 비교 가져온 comment.user_id와 req.user.id를 JavaScript에서 비교합니다. 다르면 403 반환.
14
댓글 삭제
권한 확인 후 댓글 하나를 삭제합니다. 게시글 삭제(Q8~Q9)와 달리 댓글은 다른 테이블을 참조하지 않으므로 한 번에 삭제 가능합니다.
DELETE /api/posts/:postId/comments/:commentId DELETE WHERE
routes/comments.js — DELETE /:commentId (2단계: 삭제) 
DELETE FROM comments
WHERE       id = ?          -- ? : URL 파라미터 :commentId
게시글 삭제 vs 댓글 삭제 비교
게시글 삭제 2단계 필요 — 댓글(자식)을 먼저 지우고 게시글(부모)을 지워야 합니다.
댓글 삭제 1단계로 끝 — 댓글은 다른 테이블이 참조하지 않으므로 바로 삭제 가능합니다.
