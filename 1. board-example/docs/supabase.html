우리는 지금까지 Express 서버 + SQLite로 게시판을 직접 만들었습니다. Supabase는 그 서버 자리를 대신 채워주는 PaaS(Platform as a Service)입니다. 키 관리, 행 단위 보안, 트랜잭션, 인증까지 — 직접 짜던 것들을 Supabase에서는 어떻게 다루는지 정리합니다.

1

Supabase란?

Postgres 위에 필요한 백엔드 기능을 얹어둔 서비스

Supabase는 오픈소스 Postgres 데이터베이스를 중심에 두고, 백엔드를 만들 때 반복적으로 필요한 기능들을 미리 만들어서 제공하는 서비스입니다. 우리가 board-example에서 직접 구현했던 것들과 대응해보면 이렇습니다.

우리가 직접 만든 것 (board-example) Supabase가 대신 제공하는 것
SQLite 파일 + better-sqlite3 관리형 Postgres 데이터베이스
routes/posts.js의 CRUD 라우트 테이블 스키마만 만들면 자동 생성되는 REST / GraphQL API
직접 짠 로그인·세션·비밀번호 해싱 로직 Auth (회원가입·로그인·세션·소셜 로그인)
파일 업로드 시 서버 디스크 저장 로직 Storage (파일 업로드·CDN·접근 제어)
새 댓글 알림을 위한 폴링 로직 Realtime (DB 변경 사항 구독)
Express 서버 자체 (라우팅, 인증 미들웨어 등) Edge Functions (서버 코드가 필요할 때만 작성)
ℹ️

핵심은 "서버를 안 만든다"가 아니라 "서버를 적게 만든다"입니다. 클라이언트(브라우저, 앱)가 supabase-js 라이브러리를 통해 Postgres에 직접 요청을 보내고, 대신 그 요청이 안전한지는 뒤에서 배울 RLS가 검사합니다. Express 같은 나만의 서버는 필요할 때만 추가로 둡니다.

왜 쓰는가 — 장단점

💡

장점: 서버 인프라(배포, 스케일링, 백업)를 신경 쓰지 않고 프론트엔드 개발 속도로 백엔드까지 만들 수 있습니다. 특히 CRUD 위주의 서비스, 프로토타입, 개인 프로젝트에 강합니다.

⚠️

단점: 복잡한 비즈니스 로직(여러 테이블을 얽는 트랜잭션, 외부 결제 연동, 무거운 배치 작업)은 결국 Edge Function이나 별도 서버가 필요합니다. 또한 특정 벤더(Supabase)에 구조가 묶이는 lock-in도 고려해야 합니다.

2

IaaS · PaaS · SaaS 구분법

"내가 뭘 직접 관리하는가"로 구분하면 쉽다

클라우드 서비스는 내가 직접 관리해야 하는 범위가 얼마나 줄어드는지로 구분하면 간단합니다. 아래로 갈수록(왼쪽 → 오른쪽) 내가 신경 쓸 부분이 줄고, 대신 자유도도 줄어듭니다.

On-Premise
직접 산 서버
전기·하드웨어·OS·런타임·코드 전부 직접 관리
IaaS
AWS EC2 · GCP Compute Engine
하드웨어는 빌리고, OS부터 서버 코드·DB 설치까지 직접 관리
PaaS
Supabase · Firebase · Heroku
인프라·DB·인증 같은 기반은 제공받고, 나는 데이터 모델과 기능 코드만 관리
Supabase는 여기
SaaS
Notion · Slack · Gmail
완성된 서비스를 그대로 사용, 코드를 짤 필요가 없음
🎯

간단 구분법: "서버 운영체제에 SSH로 접속해서 뭔가 설치해야 하나?" → 필요하면 IaaS. "테이블 스키마와 프론트엔드 코드만 작성하면 되나?" → PaaS. "코드 한 줄 안 짜고 그냥 가입해서 쓰나?" → SaaS. Supabase는 CREATE TABLE과 클라이언트 코드는 내가 짜지만, 서버 자체를 설치·운영할 필요는 없으므로 PaaS입니다.

언제 Supabase, 언제 직접 서버(Express 등)?

상황 추천
테이블 CRUD 위주, 빠른 MVP·개인 프로젝트 Supabase
인증·파일 업로드가 필요하지만 팀에 백엔드 인력이 적음 Supabase
여러 외부 시스템(결제, 배치, 큐)과 얽힌 복잡한 도메인 로직 직접 서버 + Supabase(DB만) 병행
학습 목적으로 요청·응답·SQL 흐름을 전부 이해하고 싶을 때 직접 서버 (지금 board-example처럼)
3

anon key vs service_role key

누가 요청하는지가 아니라, "어떤 권한으로" 요청하는지를 나타내는 키

Supabase 프로젝트를 만들면 API 키가 두 개(이상) 발급됩니다. 둘 다 JWT이고, 내부에 role 클레임만 다릅니다. 이 role 값에 따라 Postgres가 요청을 어떻게 취급할지가 결정됩니다.

anon key (public / publishable key)
브라우저·모바일 앱 등 클라이언트에 그대로 넣는 키
  • role: anon — 로그인 전 익명 사용자 권한
  • 노출돼도 괜찮도록 설계됨 (프론트 코드에 하드코딩해도 됨)
  • 실제 접근 범위는 이 키가 아니라 RLS 정책이 결정
  • 로그인한 사용자는 이 키 + 로그인 세션 토큰을 함께 사용 (role이 authenticated로 바뀜)
service_role key (secret key)
내 서버·Edge Function에서만 쓰는 키
  • role: service_role — 관리자 권한
  • RLS를 전부 무시하고 모든 행에 접근 가능
  • 절대 프론트엔드 코드나 Git 저장소에 커밋하면 안 됨
  • 서버 환경변수(.env, Secret Manager)로만 관리
클라이언트 vs 서버에서 각각 어떤 키를 쓰는지 
// 브라우저에서 실행되는 프론트 코드 — anon key
import { createClient } from '@supabase/supabase-js'

export const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY // 노출돼도 되는 키
)

// ────────────────────────────────────────

// Node.js 서버 / Edge Function — service_role key
export const supabaseAdmin = createClient(
  process.env.SUPABASE_URL,
  process.env.SUPABASE_SERVICE_ROLE_KEY, // 서버 전용, RLS 우회
  { auth: { persistSession: false } }
)
🚨

service_role 키가 유출되면 RLS는 아무 의미가 없어집니다. 이 키는 "관리자로 로그인한 것"과 같으므로, 우리가 board-example에서 비밀번호 해시나 .env의 세션 시크릿을 다루듯 똑같이 서버 밖으로 나가지 않게 관리해야 합니다.

4

RLS (Row Level Security)

"누가 이 행을 볼/고칠 수 있는가"를 테이블 안에 직접 써두는 것

우리가 만든 board-example 서버에서는 routes/posts.js 안의 코드가 "이 게시글은 작성자만 수정 가능"이라는 조건을 if (post.user_id !== req.session.userId) 처럼 직접 체크했습니다. Supabase는 클라이언트가 DB에 직접 접근하므로, 이 검사를 테이블 자체에 정책(policy)으로 등록해야 합니다. 그게 RLS입니다.

⚠️

RLS를 켜지 않으면 anon key를 가진 누구나 테이블 전체를 읽고 쓸 수 있습니다. Supabase는 테이블을 새로 만들면 기본적으로 RLS를 비활성화 상태로 두므로(과거 정책 기준, 최근엔 경고를 강하게 띄웁니다), 프로덕션에 나가기 전 반드시 켜야 합니다.

posts 테이블에 RLS 적용하기 
-- ① 테이블에 RLS 활성화 (기본값: 전체 차단)
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- ② 누구나 게시글을 읽을 수 있는 정책
CREATE POLICY "게시글은 누구나 조회 가능"
ON posts FOR SELECT
USING (true);

-- ③ 로그인한 사용자만 자기 이름으로 글을 쓸 수 있는 정책
CREATE POLICY "로그인한 사용자만 작성 가능"
ON posts FOR INSERT
WITH CHECK (auth.uid() = user_id);

-- ④ 작성자 본인만 수정/삭제할 수 있는 정책
CREATE POLICY "작성자만 수정 가능"
ON posts FOR UPDATE
USING (auth.uid() = user_id);

CREATE POLICY "작성자만 삭제 가능"
ON posts FOR DELETE
USING (auth.uid() = user_id);
▶ 클라이언트 코드는 그대로, 결과만 자동으로 필터링됨
// 로그인한 사용자로 삭제를 시도
const { error } = await supabase
  .from('posts')
  .delete()
  .eq('id', postId)
→ 코드는 남의 글이든 내 글이든 동일. 남의 글이면 정책이 막아서 0행 삭제(에러 없이 조용히 실패)로 끝난다 — 애플리케이션 코드에 권한 체크를 안 넣어도 DB가 막아준다.
💡

RLS 정책은 auth.uid()를 조건으로 걸 때 가장 강력합니다. 이 함수는 요청에 담긴 JWT에서 로그인한 사용자의 id를 꺼내옵니다. board-example의 req.session.userId와 같은 역할을, 서버 코드 없이 SQL 안에서 수행하는 것입니다.

USING vs WITH CHECK — 헷갈리는 두 조건

정책을 쓰다 보면 USING과 WITH CHECK를 같은 것으로 착각하기 쉽습니다. 역할이 다릅니다.

절 검사 대상 적용되는 명령
USING 이미 테이블에 있는 행(기존 값) — "이 행을 대상으로 삼아도 되는가" SELECT · UPDATE · DELETE
WITH CHECK 새로 쓰여지는 값(삽입/수정 후 값) — "이 값으로 써도 되는가" INSERT · UPDATE
⚠️

UPDATE 정책에 USING만 걸고 WITH CHECK를 빼먹으면, 사용자가 "자기 글을 수정"하는 김에 user_id 컬럼 값을 다른 사람 id로 바꿔서 글의 소유권을 가로챌 수 있습니다. USING은 수정 대상만 검사하고, 수정된 결과값은 검사하지 않기 때문입니다.

WITH CHECK 없이 뚫리는 예시 vs 막힌 버전 
-- ❌ USING만 있는 정책: 내 글을 남에게 "넘겨줄" 수 있다
CREATE POLICY "작성자만 수정 가능 (취약)"
ON posts FOR UPDATE
USING (auth.uid() = user_id);

-- 공격: 내 글의 user_id를 다른 사람 id로 바꿔치기 — USING 통과, 검사할 곳이 없음
-- UPDATE posts SET user_id = '다른사람_uuid' WHERE id = 내글_id;

-- ✅ WITH CHECK까지 걸어야 수정 후 값도 검사된다
CREATE POLICY "작성자만 수정 가능 (안전)"
ON posts FOR UPDATE
USING      (auth.uid() = user_id)  -- 수정 전: 내 글이어야 함
WITH CHECK (auth.uid() = user_id); -- 수정 후: user_id가 여전히 나여야 함

흔한 실수 체크리스트

실수 왜 위험한가 해결
테이블 생성 후 RLS를 그대로 꺼둠 anon key만으로 테이블 전체를 읽고·쓰고·지울 수 있음 ALTER TABLE ... ENABLE ROW LEVEL SECURITY;를 테이블 생성 직후 습관화
정책 조건에 USING (true)를 모든 명령에 그대로 씀 RLS를 켰지만 사실상 전체 허용 — RLS를 안 쓴 것과 동일 SELECT/INSERT/UPDATE/DELETE 각각 실제 필요한 조건으로 분리해서 작성
UPDATE 정책에 WITH CHECK 누락 소유권 필드(예: user_id)를 다른 값으로 바꿔치기 가능 UPDATE 정책엔 USING과 WITH CHECK를 함께 명시
클라이언트에서 select('*')로 민감 컬럼까지 조회 RLS는 행 단위 제어라 컬럼은 막아주지 않음 — 비밀번호 해시, 이메일 등이 함께 노출될 수 있음 필요한 컬럼만 명시해서 select하거나, 민감 컬럼을 제외한 뷰(view)를 만들어 그 뷰에만 접근 권한 부여
service_role 키를 프론트엔드 번들이나 Git에 커밋 RLS 자체가 완전히 무력화됨 (관리자 권한이 그대로 노출) service_role 키는 서버·Edge Function 환경변수로만 보관, .gitignore에 .env 포함
정책 테스트를 항상 service_role로만 진행 service_role은 RLS를 우회하므로, 실제 anon/authenticated 사용자 입장에서 막히는지 확인이 안 됨 Supabase 대시보드의 SQL Editor에서 SET ROLE authenticated; SET request.jwt.claims... 로 특정 사용자인 척 테스트하거나, 실제 anon key로 요청해서 검증
5

트랜잭션 처리

supabase-js는 여러 요청을 하나로 묶어주지 않는다

board-example처럼 직접 서버를 짜면 db.transaction(() => { ... })() 같은 코드로 여러 쿼리를 하나의 트랜잭션으로 묶기 쉽습니다. 그런데 supabase-js는 각 메서드 호출이 독립적인 HTTP 요청이기 때문에, 클라이언트에서 다음처럼 쓰면 트랜잭션이 보장되지 않습니다.

❌ 이렇게 하면 트랜잭션이 아니다 
// 두 요청 사이에 순서 보장도, 원자성도 없다.
// 첫 번째가 성공하고 두 번째가 실패해도 첫 번째는 그대로 반영된다.
await supabase.from('posts').update({ view_count: newCount }).eq('id', postId)
await supabase.from('post_stats').insert({ post_id: postId, event: 'view' })

해결 방법은 여러 쿼리를 Postgres 함수(RPC) 하나로 묶어서, 그 함수 자체를 하나의 트랜잭션으로 실행하는 것입니다. Postgres 함수 안에서는 여러 문장이 기본적으로 하나의 트랜잭션으로 묶입니다.

✅ Postgres 함수로 묶어서 원자적으로 처리 
-- 게시글 조회수 증가 + 통계 기록을 하나의 트랜잭션으로
CREATE OR REPLACE FUNCTION record_post_view(p_post_id bigint)
RETURNS void
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE posts
  SET view_count = view_count + 1
  WHERE id = p_post_id;

  INSERT INTO post_stats (post_id, event)
  VALUES (p_post_id, 'view');

  -- 중간에 예외가 나면 두 문장 모두 롤백된다
END;
$$;
▶ 클라이언트에서는 RPC 호출 한 번
const { error } = await supabase.rpc('record_post_view', { p_post_id: postId })
→ 두 테이블 갱신이 하나의 요청·하나의 트랜잭션으로 원자적으로 실행됨
ℹ️

Edge Function 안에서도 방법은 같습니다. Edge Function은 결국 서버 코드이므로 직접 Postgres 커넥션을 열어 BEGIN / COMMIT / ROLLBACK을 쓸 수도 있지만, 실무에서는 로직을 Postgres 함수(RPC)로 옮기는 편이 더 단순하고 재사용하기 좋습니다.

왜 원자성이 중요한가 — 은행 계좌 이체 예시

트랜잭션이 왜 필요한지는 계좌 이체로 생각하면 가장 분명합니다. "A 계좌에서 1만원을 빼고, B 계좌에 1만원을 더한다"는 두 단계 작업입니다. 이 둘은 반드시 둘 다 성공하거나, 둘 다 실패해야 합니다. 하나만 성공하면 돈이 그냥 사라지거나 복제됩니다.

🚨

따로 요청 두 번을 보내면 위험합니다. A 계좌 출금 요청이 성공한 직후 네트워크가 끊기거나 서버가 죽으면, B 계좌 입금 요청은 영영 실행되지 않습니다. A의 1만원은 이미 빠져나갔는데 B는 받지 못한, 돈이 증발한 상태로 DB가 남습니다.

계좌 이체를 하나의 트랜잭션으로 묶는 Postgres 함수 
CREATE OR REPLACE FUNCTION transfer_money(
  p_from_account bigint,
  p_to_account bigint,
  p_amount numeric
)
RETURNS void
LANGUAGE plpgsql
AS $$
BEGIN
  -- ① 출금: 잔액이 부족하면 예외를 던져서 전체를 롤백시킨다
  UPDATE accounts
  SET balance = balance - p_amount
  WHERE id = p_from_account
    AND balance >= p_amount;

  IF NOT FOUND THEN
    RAISE EXCEPTION '잔액 부족: account %', p_from_account;
  END IF;

  -- ② 입금: 여기서 문제가 생겨도 ①의 출금까지 함께 롤백된다
  UPDATE accounts
  SET balance = balance + p_amount
  WHERE id = p_to_account;

  -- ③ 이체 내역 기록도 같은 트랜잭션 안에서
  INSERT INTO transfer_logs (from_account, to_account, amount)
  VALUES (p_from_account, p_to_account, p_amount);
END;
$$;
▶ 실행 예시 — 성공 케이스
const { error } = await supabase.rpc('transfer_money', {
  p_from_account: 1,
  p_to_account: 2,
  p_amount: 10000
})
→ 1번 계좌 −1만원, 2번 계좌 +1만원, 이체 로그 1건 기록까지 전부 하나의 트랜잭션으로 커밋됨
▶ 실행 예시 — 잔액 부족 케이스 (롤백)
const { error } = await supabase.rpc('transfer_money', {
  p_from_account: 1,
  p_to_account: 2,
  p_amount: 999999999
})
// error: "잔액 부족: account 1"
→ ①에서 RAISE EXCEPTION이 발생하는 순간 함수 전체가 롤백. 2번 계좌 입금도, 이체 로그 기록도 전혀 반영되지 않고 DB는 요청 전 상태 그대로 유지됨
💡

이것이 트랜잭션의 "All or Nothing" 원칙입니다. 위의 게시글 조회수 예시와 원리는 똑같습니다 — 여러 단계의 쓰기 작업을 Postgres 함수 하나로 묶으면, 그 안에서 무슨 일이 있어도 "전부 반영" 또는 "전부 취소" 둘 중 하나만 일어납니다.

6

Auth 동작 방식

board-example의 세션 로그인과 무엇이 다른가

board-example에서는 로그인에 성공하면 서버가 세션을 만들어 쿠키로 내려주고, 이후 요청마다 req.session.userId로 사용자를 식별했습니다. Supabase Auth는 세션 대신 JWT(JSON Web Token)를 발급하고, 사용자 정보는 auth.users라는 별도 스키마 테이블에 저장합니다.

1
회원가입 — supabase.auth.signUp()
이메일·비밀번호를 보내면 Supabase가 비밀번호 해싱, auth.users에 행 생성, 이메일 인증 메일 발송까지 대신 처리합니다. 우리가 직접 짰던 bcrypt.hash() 로직이 여기 내장돼 있는 셈입니다.
2
로그인 — supabase.auth.signInWithPassword()
자격 증명이 맞으면 access token(JWT)과 refresh token을 함께 내려줍니다. access token은 짧게 만료되고, refresh token으로 조용히 재발급받습니다.
3
세션 저장 — supabase-js가 자동 처리
브라우저에서는 localStorage(또는 쿠키 기반 SSR 헬퍼)에 토큰을 저장하고, 이후 모든 요청 헤더에 Authorization: Bearer <access_token>을 자동으로 붙입니다.
4
요청마다 신원 확인 — Postgres 안의 auth.uid()
요청이 들어오면 Postgres가 JWT를 검증하고, 그 안의 사용자 id를 auth.uid() 함수로 꺼낼 수 있게 만듭니다. RLS 정책은 이 값을 조건으로 써서 "본인 데이터만" 같은 규칙을 검사합니다.

JWT 구조 자세히 보기 — role과 sub가 하는 일

board-example의 세션 쿠키는 그냥 "이 쿠키의 주인이 누구인지" DB(또는 메모리)를 찾아봐야 아는 무작위 문자열이었습니다. JWT는 다릅니다 — 토큰 자체 안에 신원 정보가 이미 들어있고, 누가 서명했는지도 검증할 수 있는 구조입니다.

JWT는 점(.) 두 개로 나뉜 3부분 
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1dWlkLW9mLWFsaWNlIiwicm9sZSI6ImF1dGhlbnRpY2F0ZWQiLCJleHAiOjE3NTE4ODQwMDB9.4f8a2c9e...서명값

// ① Header  — base64url 디코딩하면:
{ "alg": "HS256", "typ": "JWT" }

// ② Payload — base64url 디코딩하면 (이게 auth.uid()·role의 원천):
{
  "sub":   "uuid-of-alice",       // auth.uid() 가 반환하는 값
  "role":  "authenticated",      // PostgREST가 SET ROLE 할 때 쓰는 값
  "email": "alice@example.com",
  "aud":   "authenticated",
  "exp":   1751884000            // 만료 시각 (Unix timestamp)
}

// ③ Signature — 서버가 가진 JWT secret으로 ①+② 를 서명한 값
//    비밀키 없이는 위조 불가능. 검증은 서명이 일치하는지만 확인.
⚠️

Header·Payload는 암호화가 아니라 그냥 base64url 인코딩입니다. 누구나 토큰을 복사해서 디코딩하면 sub, role, email을 그대로 읽을 수 있습니다. 그래서 JWT에 비밀번호나 결제 정보 같은 민감한 값을 커스텀 클레임으로 절대 넣으면 안 됩니다 — 위조를 막는 건 ③ 서명이지, ①②를 숨기는 게 아닙니다.

클레임 어디서 쓰이는가
sub auth.uid()가 그대로 반환 → RLS 정책의 = auth.uid() 조건과 비교됨
role PostgREST가 요청 처리 직전 Postgres에 SET ROLE authenticated;(또는 anon)를 실행하는 데 사용 — 이 role이 가진 GRANT·RLS 정책이 그대로 이 요청에 적용됨
exp 만료 시각. 지났으면 서명이 맞아도 즉시 거부 → 재발급(refresh) 절차로 넘어감
aud / iat 토큰 대상(audience)·발급 시각 — 부가 검증용, 앱 로직에서 직접 쓸 일은 드묾
💡

정리하면 JWT 하나가 두 가지 역할을 동시에 합니다. role 클레임으로 "이 요청이 어떤 권한(Postgres role)으로 실행돼야 하는가"를 정하고, sub 클레임으로 "그 안에서 구체적으로 누구인가"를 알려줍니다. 오늘 얘기한 것처럼 role마다 GRANT·RLS가 다르게 걸려있으니, 이 두 클레임이 사실상 "권한 전환 스위치 + 신원 확인표" 역할을 함께 하는 셈입니다.

PostgREST 쿼리 문법

supabase-js의 select()가 실제로는 SQL로 번역된다

supabase.from(table).select() 체이닝은 결국 PostgREST라는 엔진이 HTTP 요청을 SQL로 번역해서 실행한 결과입니다. sql-concepts 문서에서 배운 JOIN·WHERE·ORDER BY·LIMIT을 클라이언트 코드로 어떻게 표현하는지 대응시켜 봅니다.

중첩 select로 JOIN 표현하기

게시글에 작성자 이름을 함께 보여주려면 SQL에서는 JOIN을 썼습니다. supabase-js에서는 외래키로 연결된 테이블을 select 안에 중첩해서 씁니다.

같은 결과, 두 가지 표현 
-- SQL: posts + users를 JOIN
SELECT   posts.id, posts.title, users.username
FROM     posts
JOIN     users ON posts.user_id = users.id;

// supabase-js: users를 posts.select() 안에 중첩
const { data } = await supabase
  .from('posts')
  .select('id, title, users(username)')
▶ 응답 형태 — 중첩 객체로 반환됨
[
  { id: 1, title: "첫 글", users: { username: "alice" } },
  { id: 2, title: "둘째 글", users: { username: "bob" } }
]
→ SQL JOIN은 평평한(flat) 행을 반환하지만, PostgREST는 관계를 users: {...} 형태로 중첩시켜 돌려줍니다. 프론트에서는 post.users.username처럼 접근합니다.

기본은 LEFT JOIN — 강제로 INNER JOIN 만들기

중첩 select는 기본적으로 LEFT JOIN처럼 동작합니다. 댓글이 하나도 없는 게시글도 comments: []로 포함됩니다. 댓글이 있는 게시글만 원한다면 !inner를 붙입니다.

!inner로 INNER JOIN처럼 강제하기 
// 댓글이 1개 이상 달린 게시글만
const { data } = await supabase
  .from('posts')
  .select('id, title, comments!inner(id)')
⚠️

중첩 테이블에 .eq()로 조건을 걸어도 상위 행은 안 걸러집니다. .select('*, comments(*)').eq('comments.approved', true)는 각 게시글의 comments 배열 안 항목만 필터링할 뿐, 승인된 댓글이 없는 게시글도 여전히 빈 배열과 함께 결과에 포함됩니다. 게시글 자체를 걸러내려면 !inner를 함께 써야 합니다.

정렬·페이지네이션 — 메서드 체이닝

SQL 절 supabase-js 메서드
ORDER BY created_at DESC .order('created_at', { ascending: false })
LIMIT 5 .limit(5)
LIMIT 5 OFFSET 10 .range(10, 14) // 0-indexed, 양끝 포함
WHERE user_id IN (1, 3, 5) .in('user_id', [1, 3, 5])

GROUP BY·HAVING·COUNT는 직접 지원되지 않는다

PostgREST는 단일 테이블 조회·필터·정렬·페이지네이션까지는 커버하지만, GROUP BY/HAVING 같은 집계 쿼리는 쿼리 빌더로 표현할 방법이 없습니다. 전체 행 개수만 필요하면 옵션으로 처리하고, 그 이상의 집계는 ⑤에서 배운 Postgres 함수(RPC)나 뷰(view)로 만들어서 호출합니다.

▶ 실행 예시 — 전체 개수만 필요할 때 (본문 데이터 없이)
const { count } = await supabase
  .from('posts')
  .select('*', { count: 'exact', head: true })
→ 행 데이터는 내려받지 않고 총 개수만 반환 — 페이지네이션 UI에 사용
8

Storage · Realtime · Edge Functions

①에서 표로만 짚었던 세 기능, 실제 코드로 보기

Storage — 파일 업로드

board-example에 이미지 첨부 기능이 있었다면 서버 디스크에 저장하고 경로를 DB에 남겼을 것입니다. Supabase Storage는 파일을 버킷(bucket) 단위로 관리하고, 업로드·다운로드 URL 발급을 클라이언트에서 바로 처리합니다.

이미지 업로드 후 공개 URL 얻기 
// 업로드
const { data, error } = await supabase.storage
  .from('post-images')
  .upload(`${postId}/${file.name}`, file)

// 공개 URL 생성 (버킷이 public일 때)
const { data: { publicUrl } } = supabase.storage
  .from('post-images')
  .getPublicUrl(`${postId}/${file.name}`)
ℹ️

버킷도 RLS와 같은 개념의 정책을 가집니다. storage.objects 테이블에 CREATE POLICY로 "본인 폴더에만 업로드 가능" 같은 규칙을 거는 방식이 테이블 RLS와 동일합니다.

왜 사진·파일은 DB가 아니라 Storage에 두는가

Postgres에도 파일을 바이트 그대로 넣을 수 있는 bytea 컬럼이 있어서, "그냥 테이블에 같이 저장하면 안 되나?"라는 생각이 들 수 있습니다. 되긴 하지만, DB와 파일 저장소는 애초에 다른 걸 잘하도록 설계된 시스템이라 실무에서는 분리합니다.

기준 DB에 파일을 직접 저장(bytea) Storage(오브젝트 스토리지)에 저장
백업·복제 DB 전체 덤프에 바이너리가 섞여 용량 폭증, 백업·복구·마이그레이션이 느려짐 파일은 별도 스토리지에 있어 DB 백업은 가볍고 빠름
커넥션 사용 대용량 전송 동안 귀한 DB 커넥션 하나를 계속 점유 → 동시 접속자 수에 영향 DB 커넥션과 무관하게 별도 경로로 전송
스트리밍·캐싱 이미지·동영상의 일부만 받는 Range 요청, CDN 캐싱을 DB가 지원하지 않음 CDN·Range 요청·브라우저 캐싱에 특화됨
비용 DB 스토리지는 고성능(디스크 IOPS 보장) 위주라 대용량 저장엔 상대적으로 비쌈 대용량 저장에 최적화되어 훨씬 저렴
인덱스·유지보수 거대한 바이너리 컬럼이 섞이면 VACUUM·인덱스 재구성 등 유지보수 작업이 느려짐 테이블은 메타데이터만 가벼워서 DB 성능에 영향 없음

그래서 Supabase Storage의 실제 구조는 "실제 바이트는 S3 호환 오브젝트 스토리지에, DB(storage.objects)에는 경로·소유자·크기 같은 메타데이터만" 두는 방식입니다. board-example을 직접 Express로 구현했다면 multer 같은 라이브러리로 파일은 서버 디스크(혹은 S3)에 저장하고, DB의 posts 테이블엔 image_url 컬럼처럼 경로 문자열만 남기는 것과 정확히 같은 설계 원칙입니다 — 관계형 DB는 "구조화된 데이터와 관계"를 다루는 데, 파일 저장소는 "큰 바이너리를 빠르게 서빙"하는 데 최적화돼 있기 때문입니다.

💡

예외적으로 DB에 직접 넣는 게 나은 경우도 있긴 합니다. 아주 작은 파일(수 KB짜리 아이콘 등)이면서, 파일과 다른 데이터가 하나의 트랜잭션으로 반드시 함께 commit/rollback돼야 하는 특수한 경우입니다. 하지만 게시글 이미지·첨부파일처럼 일반적인 용도라면 거의 항상 Storage(또는 S3 등 오브젝트 스토리지)가 맞는 선택입니다.

Realtime — DB 변경 사항 구독

새 댓글이 달렸는지 확인하려고 몇 초마다 다시 요청을 보내는(폴링) 대신, Realtime은 DB 변경 이벤트를 구독해서 변경이 생기는 즉시 클라이언트로 밀어줍니다.

특정 게시글의 새 댓글 실시간 구독 
supabase
  .channel('comments-changes')
  .on(
    'postgres_changes',
    { event: 'INSERT', schema: 'public', table: 'comments', filter: `post_id=eq.${postId}` },
    (payload) => {
      // payload.new 에 방금 삽입된 댓글 행이 그대로 들어있다
      appendComment(payload.new)
    }
  )
  .subscribe()
⚠️

Realtime 방송도 RLS의 영향을 받습니다. 구독한 사용자가 원래 RLS 정책상 볼 수 없는 행이라면 변경 이벤트도 전달되지 않습니다 — "실시간이니까 예외"는 없습니다.

Edge Functions — 서버 코드가 꼭 필요할 때

RLS와 RPC로 못 푸는 일도 있습니다. 외부 결제 API 호출, 이메일 발송, 웹훅 처리처럼 Supabase 바깥 세상과 통신해야 하거나 service_role 권한이 필요한 로직은 Edge Function(Deno 런타임의 서버리스 함수)에 넣습니다.

supabase/functions/notify-author/index.ts 
Deno.serve(async (req) => {
  const { postId, commenterName } = await req.json()

  // 여기서만 service_role 키를 안전하게 쓸 수 있다 (서버 환경)
  const admin = createClient(SUPABASE_URL, SERVICE_ROLE_KEY)
  const { data: post } = await admin.from('posts').select('*').eq('id', postId).single()

  await sendEmail(post.author_email, `${commenterName}님이 댓글을 남겼습니다`)

  return new Response('ok')
})
▶ 클라이언트에서 호출
await supabase.functions.invoke('notify-author', {
  body: { postId, commenterName: 'bob' }
})
→ 클라이언트는 anon key로만 호출하고, 위험한 로직·비밀키는 함수 안에 숨겨짐
💡

구분 기준: DB 안에서 여러 테이블을 원자적으로 갱신하는 정도라면 ⑤의 RPC(Postgres 함수)로 충분합니다. Supabase 바깥의 API·이메일·결제와 통신해야 하거나 service_role이 필요하면 Edge Function으로 넘깁니다.

9

로컬 개발 워크플로우

board-example의 seed.sql·Makefile과 같은 목적, 다른 도구

board-example에서는 Makefile과 seed.sql로 "누가 실행해도 똑같은 DB 상태"를 재현했습니다. Supabase는 Supabase CLI로 같은 문제를 풉니다 — 로컬에 전체 스택을 띄우고, 스키마 변경을 마이그레이션 파일로 코드화합니다.

1
supabase init
프로젝트에 supabase/ 폴더(설정 파일, migrations/)를 생성합니다.
2
supabase start
Docker로 로컬에 Postgres·Auth·Storage·Studio 전체 스택을 그대로 띄웁니다. 이때부터는 실제 프로젝트 없이 내 컴퓨터에서 전부 테스트할 수 있습니다.
3
supabase migration new add_posts_table
타임스탬프가 붙은 마이그레이션 SQL 파일이 생성됩니다. board-example의 schema.sql을 한 번에 두는 대신, 변경 하나하나를 파일로 남기는 방식입니다.
4
supabase db reset
로컬 DB를 비우고 migrations/에 있는 파일을 순서대로 전부 재적용합니다. board-example에서 make seed로 더미 데이터를 다시 채우던 것과 같은 역할을, 스키마 변경 이력까지 포함해서 재현합니다.
5
supabase link --project-ref <ref>
로컬 프로젝트를 실제 Supabase 클라우드 프로젝트와 연결합니다.
6
supabase db push
로컬에서 만든 마이그레이션을 원격(프로덕션) DB에 순서대로 적용합니다. 스키마 변경이 코드 리뷰·Git 히스토리로 남는 이유입니다.
터미널에서 한 번에 보는 전체 흐름 
# 최초 1회
npx supabase init
npx supabase start                              # 로컬 스택 기동

# 스키마를 바꿀 때마다
npx supabase migration new add_posts_table       # migrations/xxxx_add_posts_table.sql 생성
# → 파일 안에 CREATE TABLE / ALTER TABLE 등을 직접 작성
npx supabase db reset                            # 로컬 DB에 전체 마이그레이션 재적용

# 원격 프로젝트에 반영할 때
npx supabase link --project-ref abcdefghijk
npx supabase db push                             # 로컬 migrations → 프로덕션 DB
💡

migrations/ 폴더는 반드시 Git에 커밋합니다. board-example에서 schema.sql·seed.sql을 저장소에 커밋해서 누구나 같은 DB를 재현할 수 있게 한 것과 같은 이유입니다 — 스키마의 변경 이력 자체가 코드로 관리되어야 팀원 전체와 프로덕션이 항상 같은 상태를 유지할 수 있습니다.
