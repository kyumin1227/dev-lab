認証 — auth.js

会員登録・ログイン処理 / routes/auth.js
1
ユーザー名の重複確認
会員登録時に、入力されたユーザー名がすでに存在するかを先に確認します。存在していれば登録を止めて 409 エラーを返します。
POST /api/auth/register SELECT WHERE
routes/auth.js — POST /register 
SELECT id
FROM   users
WHERE  username = ?          -- ? にはユーザーが入力したユーザー名が入る
各句の説明
SELECT id 存在確認だけでよいので、id だけを取得します。SELECT * だと不要な データ（パスワードなど）まで読んでしまうため避けます。
FROM users users テーブルを検索します。
WHERE 特定の username を持つ行だけに絞り込みます。? はプレースホルダで、実際の値は コード側で安全にバインドされます（SQL インジェクション対策）。
💡

結果があれば すでに使われているユーザー名なので 409 を返します。結果がなければ 次の段階（INSERT）へ進みます。

2
会員登録 — ユーザー追加
重複確認を通過したあと、ハッシュ化したパスワードと一緒に新しいユーザーを保存します。
POST /api/auth/register INSERT
routes/auth.js — POST /register 
INSERT INTO users (username, password)
VALUES (?, ?)     -- ? : ユーザー名、bcrypt でハッシュ化したパスワード
各句の説明
INSERT INTO 指定したテーブルに新しい行を追加します。
(username, password) 値を入れるカラムを明示します。id と created_at は書かなくても DB が 自動で補います。
VALUES 挿入する値を順番に指定します。password はコード側で bcrypt.hashSync() によりハッシュ化してから渡されます。
⚠️

パスワードを平文で保存してはいけません。 DB には bcrypt でハッシュ化した値を 保存します。ハッシュは一方向なので、元のパスワードを逆算できません。

3
ログイン — ユーザー取得
ユーザー名でユーザーを検索し、パスワードハッシュを取得します。その後、コード側で入力されたパスワードと ハッシュを照合して認証します。
POST /api/auth/login SELECT WHERE
routes/auth.js — POST /login 
SELECT *
FROM   users
WHERE  username = ?
各句の説明
SELECT * ユーザーの全カラムを取得します。パスワードハッシュの比較と JWT トークン発行のために id、 username、password のすべてが必要だからです。
WHERE 入力されたユーザー名に一致するユーザー1件だけを取得します。username には UNIQUE 制約があるため、結果は常に 0 件または 1 件です。
💡

クエリ結果がなければ存在しないユーザー名、結果があっても bcrypt.compareSync() が false なら パスワード不一致です。どちらも同じ 401 として処理します（どちらが間違っているかを明かさない方が安全です）。

📝

投稿 — posts.js

一覧・詳細取得、作成、削除 / routes/posts.js
4
投稿一覧取得
メイン画面に表示する投稿一覧です。各投稿の投稿者名とコメント数もあわせて取得します。 このサービスの中では最も複雑なクエリです。
GET /api/posts SELECT JOIN × 2 GROUP BY
routes/posts.js — GET / 
SELECT   posts.id,
         posts.title,
         posts.created_at,
         users.username,
         COUNT(comments.id) AS comment_count
FROM     posts
JOIN     users    ON posts.user_id  = users.id
LEFT JOIN comments ON comments.post_id = posts.id
GROUP BY posts.id
ORDER BY posts.created_at DESC
各句の説明
SELECT で列を指定 必要なカラムだけを明示的に選びます。posts.id のように テーブル.カラム 形式で 書くのは、2つのテーブルに同名のカラム（id、created_at）があり、 どちらのものか明確にする必要があるためです。
COUNT(comments.id) 各投稿についたコメント数を数えます。COUNT(*) ではなく COUNT(comments.id) を 使うのは、コメントが 0 件の投稿では LEFT JOIN 後の comments.id が NULL になり、 COUNT は NULL を数えないため正しく 0 を返せるからです。
JOIN users posts テーブルには user_id（数値）しかなく、投稿者名はありません。INNER JOIN で users テーブルをつなぎ、username を取得します。投稿者は必ず存在する前提なので INNER JOIN を 使っています。
LEFT JOIN comments コメントが 1 件もない投稿も一覧に出す必要があるため、LEFT JOIN を使います。INNER JOIN にすると コメントがない投稿は結果から落ちてしまいます。
GROUP BY posts.id LEFT JOIN によりコメント数ぶん行が増えるため（投稿 1 件にコメント 3 件なら 3 行）、 GROUP BY で投稿単位にまとめ直します。このとき COUNT() が各グループの コメント数を計算します。
ORDER BY … DESC 新しい投稿が上に来るように降順で並べます。
🔍

LEFT JOIN と INNER JOIN の違い: コメントがない投稿も含めるには LEFT JOIN が必須です。 INNER JOIN は両方のテーブルで一致する行だけを結果に含めます。

5
投稿詳細取得
特定の投稿 1 件を ID で取得します。詳細ページに入るときに実行されます。
GET /api/posts/:id SELECT JOIN WHERE
routes/posts.js — GET /:id 
SELECT   posts.*,
         users.username
FROM     posts
JOIN     users ON posts.user_id = users.id
WHERE    posts.id = ?          -- ? : URL パラメータ :id
各句の説明
posts.* posts テーブルの全カラムを取得します。詳細ページではタイトル・本文・作成日時をすべて表示する必要があります。 users.* ではなく posts.* だけを使うのは、users の password が含まれるのを防ぐためです。
JOIN users 投稿者名を取得するために JOIN します。考え方は Q4 と同じです。
WHERE posts.id = ? URL の :id パラメータで特定の投稿 1 件だけに絞ります。id は PK（主キー）なので、結果は 0 件または 1 件です。
6
投稿作成
ログイン済みユーザーが新しい投稿を作成するときに実行されます。JWT トークンの検証後にのみ動きます。
POST /api/posts INSERT
routes/posts.js — POST / 
INSERT INTO posts (title, content, user_id)
VALUES (?, ?, ?)   -- ? : タイトル、本文、ログイン中ユーザーの id
各句の説明
(title, content, user_id) この 3 カラムだけを指定します。id は AUTOINCREMENT、created_at は DEFAULT CURRENT_TIMESTAMP により DB が自動で埋めます。
user_id = req.user.id 3 つ目の ? には JWT トークンから取り出したログイン中ユーザーの ID が入ります。 フロントが直接 user_id を送るのではなく、サーバーがトークンから取り出すので改ざんできません。
7
投稿削除前 — 存在確認と権限確認
削除リクエストが来たら、まず投稿が存在するか、そしてリクエストした人が投稿者本人かを確認します。 このクエリで確認してから実際の削除クエリを実行します。
DELETE /api/posts/:id SELECT WHERE
routes/posts.js — DELETE /:id（1段階目: 確認） 
SELECT *
FROM   posts
WHERE  id = ?            -- ? : URL パラメータ :id
各句の説明 + コードとの連携
結果なし 投稿が存在しない → コード側で 404 を返す。
post.user_id を比較 取得した post.user_id と JWT トークンの req.user.id をコード側で比較します。 一致しなければ 403 を返します。この判定は SQL ではなく JavaScript で行います。
⚠️

権限確認は絶対に省略してはいけません。 確認せずに DELETE を実行すると、誰でも他人の投稿を 削除できてしまいます。

8
投稿削除時 — 先にコメントを削除
投稿についたコメントは posts テーブルを参照しています。先に投稿を削除すると参照整合性エラーになるため、 コメントを先に削除します。
DELETE /api/posts/:id DELETE WHERE
routes/posts.js — DELETE /:id（2段階目: コメント削除） 
DELETE FROM comments
WHERE       post_id = ?      -- ? : 削除する投稿 id
各句の説明
DELETE FROM comments posts テーブルではなく comments テーブルの行を削除します。
WHERE post_id = ? その投稿についたコメントだけを削除します。WHERE なしで実行すると全コメントが消えてしまうため必須です。
💡

実務では CASCADE で自動化することが多いです。 FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE を定義しておけば、 投稿削除時にコメントも自動で削除されます。このサービスでは手動で処理しています。

9
投稿削除
コメントを先に削除してから、実際の投稿を削除します。Q8 → Q9 の順で実行されます。
DELETE /api/posts/:id DELETE WHERE
routes/posts.js — DELETE /:id（3段階目: 投稿削除） 
DELETE FROM posts
WHERE       id = ?          -- ? : 削除する投稿 id
実行順の整理
① Q7 投稿の存在確認・権限確認（SELECT）
② Q8 その投稿のコメントをすべて削除（DELETE FROM comments）
③ Q9 投稿を削除（DELETE FROM posts）— この順番でないと外部キーエラーなしに削除できません。
💬

コメント — comments.js

コメント一覧・作成・削除 / routes/comments.js
10
コメント一覧取得
投稿詳細ページで、その投稿についたコメントをすべて取得します。投稿者名もあわせて、古い順に並べます。
GET /api/posts/:postId/comments SELECT JOIN WHERE
routes/comments.js — GET / 
SELECT   comments.*,
         users.username
FROM     comments
JOIN     users ON comments.user_id = users.id
WHERE    comments.post_id = ?    -- ? : URL パラメータ :postId
ORDER BY comments.created_at ASC
各句の説明
comments.* コメントの全カラムを取得します。Q5 の posts.* と同じ考え方で、users.* は使わないためパスワードが 表に出ることはありません。
JOIN users comments テーブルには user_id しかないため、JOIN で投稿者名を取得します。
WHERE comments.post_id = ? その投稿のコメントだけに絞り込みます。この条件がないと全コメントが返ってしまいます。
ORDER BY … ASC 先についたコメントが上に来るように昇順で並べます。投稿一覧（Q4）とは逆方向です。
11
コメント作成前 — 投稿存在確認
コメントを作成する前に、その投稿が本当に存在するかを確認します。削除済みの投稿にコメントが付くのを防ぎます。
POST /api/posts/:postId/comments SELECT WHERE
routes/comments.js — POST /（1段階目: 確認） 
SELECT id
FROM   posts
WHERE  id = ?            -- ? : URL パラメータ :postId
各句の説明
SELECT id Q1 と同じパターンです。存在確認だけが目的なので id だけを取得します。
結果なし → 404 投稿がなければ 404 を返し、INSERT は実行しません。
12
コメント作成
投稿の存在を確認したあと、コメントを保存します。
POST /api/posts/:postId/comments INSERT
routes/comments.js — POST /（2段階目: 挿入） 
INSERT INTO comments (content, post_id, user_id)
VALUES (?, ?, ?)   -- ? : コメント本文、投稿 id、ログイン中ユーザー id
各句の説明
post_id URL パラメータ :postId から受け取ります。どの投稿へのコメントかを外部キーで結び付けます。
user_id Q6（投稿作成）と同じく、JWT トークンから取り出した req.user.id が入ります。
13
コメント削除前 — 存在確認と権限確認
Q7（投稿削除前の確認）と同じパターンです。コメントが存在するか、リクエストした人が投稿者本人かを確認します。
DELETE /api/posts/:postId/comments/:commentId SELECT WHERE
routes/comments.js — DELETE /:commentId（1段階目: 確認） 
SELECT *
FROM   comments
WHERE  id = ?            -- ? : URL パラメータ :commentId
各句の説明
結果なし → 404 コメントがすでに削除されている、または存在しない場合は 404 を返します。
comment.user_id を比較 取得した comment.user_id と req.user.id を JavaScript で比較します。 一致しなければ 403 を返します。
14
コメント削除
権限確認のあと、コメント 1 件を削除します。投稿削除（Q8〜Q9）と違って、コメントは他テーブルから 参照されていないため 1 回で削除できます。
DELETE /api/posts/:postId/comments/:commentId DELETE WHERE
routes/comments.js — DELETE /:commentId（2段階目: 削除） 
DELETE FROM comments
WHERE       id = ?          -- ? : URL パラメータ :commentId
投稿削除とコメント削除の比較
投稿削除 2 段階必要 — 先にコメント（子）を消してから投稿（親）を削除する必要があります。
コメント削除 1 段階で完了 — コメントは他テーブルから参照されていないので、そのまま削除できます。
