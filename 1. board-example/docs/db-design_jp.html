ファイル保存との違い

フロントエンドで localStorage に保存したり、 JSONファイルとして保存したりするだけではダメなのでしょうか？

項目 ファイル / localStorage データベース

キー（Key）完全攻略

テーブル内のデータを識別し、関連付ける方法

データベースにおける キー（Key）とは、 テーブル内の行（Row）を識別したり、 他のテーブルと関連付けたりするための仕組みです。 掲示板システムで使用される4種類のキーについて見ていきましょう。

🔑 主キー（Primary Key）

テーブル内の各行を 一意に識別する カラムです。 重複はできず、NULLも許可されません。

このような役割があります
  • 各行で必ず異なる値を持つ
  • NULL（空の値）は不可
  • 1つのテーブルに1つだけ存在できる
  • AUTOINCREMENTによりDBが自動採番する
掲示板の主キー 
-- すべてのテーブルの id が主キー
id INTEGER PRIMARY KEY AUTOINCREMENT

-- users: id=1, id=2, id=3...
-- posts: id=1, id=2, id=3...
-- comments: id=1, id=2, id=3...

🔗 外部キー (Foreign Key)

他のテーブルの主キーを 参照する カラムです。 テーブル同士の関係を作るための つながり（リンク）となります。

このような役割があります
  • 参照先のテーブルに実際に存在する値しか登録できない
  • 存在しない user_id を持つ投稿は作成できない
  • テーブル間の関係をDBが自動的に保証する
掲示板の外部キー 
-- posts.user_id → users.id を参照
user_id INTEGER,
FOREIGN KEY (user_id)
  REFERENCES users(id)

-- comments には外部キーが2つある
FOREIGN KEY (post_id) REFERENCES posts(id)
FOREIGN KEY (user_id) REFERENCES users(id)

🚫 ユニークキー（Unique Key）

主キーと同様に 重複を許可しませんが、 NULLは許可され、 1つのテーブルに複数設定することができます。

主キーとの違い
項目 PK UQ
重複不可 ✅ ✅
NULL不可 ✅ ❌
テーブルごとの数 1つのみ 複数設定可能
掲示板における UNIQUE 制約 
-- 同じユーザー名では登録できない
username TEXT UNIQUE NOT NULL

-- すでに alice が存在する場合
INSERT INTO users (username...)
VALUES ('alice'...)
-- → UNIQUE constraint failed エラー

🔑🔑 複合主キー（Composite Key）

2つ以上のカラムを組み合わせて 主キーとして使用します。 各カラムは重複していても構いませんが、 その組み合わせは一意でなければなりません。

「いいね」テーブルでの例

user_id post_id 登録可能？
1 1 ✅ 初回のいいね
1 2 ✅ 別の投稿
2 1 ✅ 別のユーザー
1 1 ❌ 重複！
複合主キーの定義 
CREATE TABLE likes (
            user_id INTEGER,
            post_id INTEGER,

            -- 2つのカラムの組み合わせを主キーにする
            PRIMARY KEY (user_id, post_id)
          );

キーの種類まとめ

種類 役割 掲示板での例
PK 主キー 行を一意に識別する users.id, posts.id, comments.id
FK 外部キー 他のテーブルを参照する posts.user_id, comments.post_id
UQ ユニークキー 重複を防ぐ users.username
CPK 複合主キー 複数のカラムの組み合わせで識別する likes(user_id, post_id)

データ型

どの値を、どの型で保存するか

テーブルを設計するときは、各カラムに どの種類のデータを入れるか を決める必要があります。 型が合っていないと、保存も計算も正しく行えません。

INTEGER
整数

小数点のない数値です。`id`、件数、順番などに使います。

id = 1 user_id = 3 like_count = 42
掲示板: id, user_id, post_id
TEXT
文字列

長さに制限のない文字列です。 ユーザー名、タイトル、本文など、 ほとんどの文字データに使用します。

username = "alice" title = "最初の投稿"
掲示板: username, title, content, password
REAL
実数（小数）

小数点を含む数値です。 価格、評価、緯度・経度などに使用します。

price = 9900.50 rating = 4.5 lat = 37.5665
掲示板: 該当なし
DATETIME
日付＋時刻

日付と時刻をまとめて保存します。 作成日時、更新日時、有効期限などに使用します。

created_at = "2026-05-20 09:30:00"
掲示板: created_at
BOOLEAN
真偽値

真(1) または偽(0)を表します。有効・無効、公開・非公開、既読・未読などに使います。

is_active = 1 is_public = 0 is_read = 1
SQLiteでは内部的に
INTEGER の 0/1 として扱う
BLOB
バイナリ

画像やファイルなどのバイナリデータです。実務ではファイル本体よりも 保存先パス（URL）を TEXT で持たせることが多いです。

thumbnail_url = "/images/abc.jpg"
多くの場合は URL を
TEXT で保存

型を選ぶ基準

場面 型 理由
ユーザー ID、投稿番号 INTEGER 数値演算・比較がしやすく、JOIN に向く
名前、タイトル、本文 TEXT 長さを固定しづらく、自由な文字列を扱える
価格、評価 REAL 小数点が必要
作成日、更新日 DATETIME 日時の比較・並び替えができる
公開状態、有効化状態 INTEGER (0/1) BOOLEAN 型を持たない DB も多い
画像、添付ファイル TEXT (URL) ファイル本体は S3 などへ保存し、DB にはパスだけを持たせる
⚠️

電話番号は INTEGER ではなく TEXT で保存します。 `010-1234-5678` のようにハイフンを含むことがあり、 先頭の 0 が落ちる問題もあるためです。

ERD — 設計図の読み方

Entity Relationship Diagram

ERD はデータベースの 設計図です。コードを書く前に、テーブル構造と関係性を 視覚的に整理します。

掲示板 ERD — ERDCloud
PK Primary Key — 主キー（行を一意に識別） FK Foreign Key — 外部キー（他テーブルを参照） UQ Unique — 重複不可 NN Not Null — NULL不可
📐

先に ERD を描く理由: 実装中に設計ミスへ気づくと、全体を大きく作り直すことになります。 設計段階で ERD を確認しておけば、修正コストはかなり抑えられます。

  FOREIGN KEY (post_id) REFERENCES posts(id),   ← 外部キー

リレーション — 1:N を理解する

テーブル同士がどうつながるか

掲示板のリレーションはすべて 1:N（一対多） です。"1" 側の1つに対して、"N" 側の複数が結びつきます。

👤 users
1人
1 : N
複数の投稿を書く
📝 posts
N件
1 : N
複数のコメントが付く
💬 comments
N件
🎯

設計のルール: 1:N では外部キーを必ず "N" 側のテーブルに置きます。
ユーザー1人に対して投稿が N 件あるので、user_id は posts テーブルに入ります。

データで理解する

users.id username posts.id title user_id
1 alice → 1 1つ目の投稿 1
2 bob → 2 2つ目の投稿 2
→ 3 3つ目の投稿 1

alice(id=1) は投稿 1 番・3 番を、bob(id=2) は 2 番を作成しています。`user_id` が接続の鍵です。

外部キーとデータ整合性

DB が自動でデータを守る仕組み

外部キーは単なる数字ではありません。DB が参照整合性を自動で保証します。

❌ 外部キーが防いでくれるケース

  • 存在しない `user_id` を持つ投稿を作ろうとする
  • コメント付きの投稿を、コメント未削除のまま消そうとする
  • 退会済みユーザーの id を新規投稿に紐づけようとする
⚠️

削除順序が重要です。 投稿を削除するときは、先に関連コメントを削除する必要があります。
親の `posts` を先に消すと、子の `comments` の外部キー参照先がなくなりエラーになります。 

// routes/posts.js — 順序が重要
db.prepare("DELETE FROM comments WHERE post_id = ?").run(id);  ← 子を先に削除
db.prepare("DELETE FROM posts WHERE id = ?").run(id);           ← 親をあとで削除

実習 — いいね機能を設計する

N:M 関係と中間テーブル
🖊 実習課題

投稿にいいね機能を追加するとしたら？

1人のユーザーが複数の投稿にいいねでき、
1つの投稿に複数のユーザーがいいねできます。

ERDCloud で `likes` テーブルを自分で設計してみましょう。

ヒント — なぜ中間テーブルが必要なのか

`users` と `posts` は N:M（多対多） の関係です。1:N と違って、片側に外部キーを置くだけでは 表現できません。

👤 users
N人
N : M
📝 posts
M件
↓ N:M は中間テーブルに分解する
👤 users
1 : N
❤️ likes
(中間テーブル)
N : 1
📝 posts

解答 — `likes` テーブル設計

likes テーブル 
CREATE TABLE likes (
  user_id    INTEGER NOT NULL,
  post_id    INTEGER NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, post_id),            ← 複合キー: 同じ人が同じ投稿へ重複いいね不可
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (post_id) REFERENCES posts(id)
);
💡

複合主キー: PRIMARY KEY (user_id, post_id) は、2つのカラムの組み合わせが一意でなければならない という意味です。同じ人が同じ投稿に2回いいねしようとすると、DB が自動で防ぎます。

設計原則のまとめ

良い設計を判断する基準

AI は SQL クエリを代わりに書けますが、設計を判断するのは人です。 絶対的な正解はなく、 状況に応じたトレードオフを選ぶことが重要です。

1つのカラム = 1つの値

配列や JSON を1セルに詰め込みません。後から検索や更新がしづらくなるためです。（意図的な例外は可）

重複データは分離する

同じ情報が複数箇所に繰り返し現れるなら、テーブルを分けます。修正時に1か所だけ直せば済みます。

N:M は中間テーブルへ

多対多の関係は直接持たず、1:N を2本に分けて表現します。

完璧な設計はない

正規化 vs 性能、単純さ vs 拡張性。状況に合わせてトレードオフを選びます。

🎓

AI 時代の DB 力: SQL 文法の暗記よりも、 どんなテーブルを作り、関係をどう張るか のほうが重要です。設計を明確に説明できれば、 AI が残りのクエリ作成を助けてくれます。

正規化の基礎

重複を減らし、構造を整える方法

正規化（Normalization）とは、テーブルの重複や異常（anomaly）を減らすために構造を 段階的に整えていく考え方です。1NF → 2NF → 3NF の順に、条件は少しずつ厳しくなります。

① 1NF — 原子値（Atomic Values）

1つのセルには 1つの値だけが入るべきです。リストや配列を1セルに入れると 1NF 違反になります。

❌ 1NF 違反
`posts` テーブルにタグ一覧を1セルへ詰め込んでいる
id title tags
1 お知らせ 告知, イベント, 重要
2 質問があります 質問, ヘルプ募集
1セルに複数の値が入っており、検索・更新がしづらい状態です。
✅ 1NF 準拠
タグを `post_tags` テーブルへ分離して1行1値にする
post_id tag
1 告知
1 イベント
1 重要
2 質問
各行が1つのタグだけを持つので、集計や絞り込みがしやすくなります。

② 2NF — 部分関数従属の排除（No Partial Dependency）

複合主キーを持つテーブルでは、一般カラムは 主キー全体 に従属していなければなりません。主キーの 一部だけに従属していると 2NF 違反です。

❌ 2NF 違反（複合キー: `post_id + user_id`）
`username` が複合キー全体ではなく `user_id` のみに従属している
post_id user_id username
1 10 alice
2 10 alice
同じ `username` が繰り返し保存され、更新漏れの原因になります。
✅ 2NF 準拠（`users` テーブルへ分離）
投稿へのいいね情報とユーザー情報を役割ごとに分ける
post_id user_id
1 10
2 10
＋
id username
10 alice
ユーザー名は `users` にだけ置くので、修正は1か所で済みます。
💡

この掲示板の `posts` テーブルは単一主キー（id）なので、2NF の問題は起きません。2NF は主に 複合主キーを使うテーブル（例: `post_tags`, `likes`）で注意が必要です。

③ 3NF — 推移的従属の排除（No Transitive Dependency）

一般カラムは主キーにのみ従属すべきです。一般カラム A → 一般カラム B のような従属（推移的 従属）があると 3NF 違反です。

❌ 3NF 違反
`posts` テーブルにユーザーのメールアドレスまで持たせている
id title user_id user_email
1 お知らせ 10 a@example.com
2 質問 10 a@example.com
`id → user_id → user_email` の推移的従属があり、メールアドレスが重複します。
✅ 3NF 準拠
投稿とユーザー情報を分離し、`user_id` でつなぐ
id title user_id
1 お知らせ 10
2 質問 10
＋
id email
10 a@example.com
メールアドレスは `users` にだけ存在するため、冗長性がなくなります。

正規化ステップの要約

段階 条件 違反例 解決方法
1NF 各セルに原子値を1つだけ tags = "告知,イベント" tags 専用テーブルへ分離
2NF 部分従属がない（複合キー） likes に username を保存 users テーブルへ分離
3NF 推移的従属がない posts に user_email を保存 users テーブルへ分離

意図的な非正規化 — どんなときにルールを崩すのか

正規化が常に唯一の正解とは限りません。性能・利便性・アーキテクチャの都合で、意図的に 正規化を崩すこともあります。

PostgreSQL 配列型

1つのセルに複数値を保存する方法です（1NF 違反）。タグや権限のように単純な一覧参照だけなら、別テーブルより 速くて簡単な場合があります。

MSA（マイクロサービス）

サービスごとに DB を分離し、同じデータを複数の DB に重複保存します。独立デプロイや拡張性のための 意図的な選択です。

キャッシュ・集計カラム

コメント数を毎回 `COUNT` せず、`posts.comment_count` に保存します。参照性能のために重複を許容します。
